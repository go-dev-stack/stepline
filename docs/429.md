# 429 and why the limiter does not handle it

Only the problem, no solutions; the rule itself is in the README.

## The provider limit and 429

The provider counts our calls and answers 429 when we cross its limit. The
limiter's only job is to space our calls so this never happens. It does not
react to a 429. The caller gets it like any other error. A retry calls
`Wait` again and is paced like every call.

When strict spacing is in place, a 429 can still come from these places:

| Source | Kind |
|---|---|
| A call on the same provider budget that does not go through the Limiter | wiring mistake |
| Retries that call the provider again without calling `Wait` first | wiring mistake |
| Stale config after the provider lowered the limit, e.g. a cheaper plan | ops mistake |
| Two limiter keys mapped to one provider budget | key design mistake |
| Redis down, the limiter fails open and calls go out unpaced | documented degrade |
| Provider window edge: exactly N calls in a window the provider counts inclusively | config, use N-1 |
| Provider malfunction or global throttling | provider fault, same as a 503 |
| Burst limit, once burst mode exists | future |

Every row is a mistake, a fault or a documented degrade. None is normal
behaviour the limiter should absorb. The two most likely ones in practice:

- New code calls the same provider budget without going through the
  Limiter. The Limiter cannot see those calls.
- The provider plan changes and the configured rate stays as it was.

Both are operations mistakes. The fix is outside this package: send every
call through the Limiter, keep the configured rate equal to the plan.

## Exclusive caller

The limiter must be the only path to the provider for a given budget. The
package assumes the limit is not shared between limited and unlimited
callers. There is no way to detect a violation from inside; the symptom is
429s that the retries absorb silently. Counting the 429s your callers see
is the only signal.
